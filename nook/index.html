The Nook

Starlings nest in enclosed spaces, and this is where Sarlin packages live. Each package stays in its own GitHub repository; the Nook lists which packages exist and which versions they have published.

Using packages

Packages are managed by the sarlin command, run from a project folder:

Adding a package writes one require: line to sarlin.project and records the exact commit in sarlin.lock, so builds are repeatable.

Sarlin has no namespaces yet, so two packages that define the same name cannot be built together. sarlin collisions lists every name defined more than once and where, and it runs automatically after add and update. The package documentation covers everything in detail.

How packages are checked

Nothing in the Nook is reviewed by hand unless a check asks for it, and nothing from a package is ever run by the checks: they read and type-check the source only.

Listing a package

A pull request that adds or changes a package entry gets a comment with a table of results and one of three outcomes:

  • Approved: every check passed, so the pull request is merged automatically and the package appears within a minute.
  • Needs manual review: a maintainer must look at it. This is not a failure. It marks something a person should confirm, such as a first contribution, a young account, a repository that belongs to someone else, or a name close to an existing one.
  • Rejected: a check found a problem, such as an invalid entry, a repository that cannot be read, a package that defines func main, or a secret in the source. Fix it and push again, and the checks rerun.

The checks cover the author (account age, earlier contributions, whether they own the repository), the repository (public, not a fork, licence), the name (reserved names, near-copies of existing names) and a scan of the package itself.

Every new version

Tagging a new version of a listed package does not need a pull request, so every new version goes through the same package scan before it is published. A version that passes appears in the list. A version that does not is held back, and an issue describes why. Versions already published are never changed or rescanned.

  • Embedded native code (external functions) and network use always need a person to approve them, because they run native code on the machine of everyone who builds with the package.
  • The scan also looks for hidden or look-alike characters, secrets, access to sensitive paths, obfuscated blobs, history rewrites, a version that suddenly gains new abilities, licence mismatches and copies of other packages.
  • A maintainer can approve a held version, except one with a blocking finding; the author releases a fixed version instead. A bad version that was published can be yanked: it disappears from search and from new installs, while existing lock files keep working.
  • Each package is also built against the newest Sarlin release, and the list shows whether it still compiles.

Every threshold and switch is in the Nook's policy file, and the README lists every check. To report a malicious or broken package, see the security policy.

Publishing a package

  1. Put the package in a public GitHub repository. It is an ordinary Sarlin project, with its files under source/ and no func main.
  2. Tag a release such as v0.1.0. Each tag is a version.
  3. Open a pull request to the Nook that adds packages/<name>.package:

The pull request is checked automatically and, when every check is clean, merged automatically. After that, new versions need no further changes: tag a release and it is picked up within the hour. A published version is pinned to the commit it had when it was first seen, so release a new version rather than moving a tag.
