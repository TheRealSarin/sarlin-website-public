Packages

0.1.5

Adding code written by other people to a project, and publishing your own.

Requires Sarlin 0.1.3

Package commands were added in 0.1.3. Earlier compilers reject sarlin add and do not understand require: lines. The commands package-search, package-info, package-list and update --check were added in 0.1.5. Packages are fetched with git, which must be installed. A project that requires no packages never uses git.

Overview

A package is an ordinary Sarlin project kept in its own GitHub repository. Adding one downloads its source and compiles it together with your own files, so everything the package defines becomes available in your project. The Nook is the public list of packages; each entry records where a package lives and which versions it has published.

Every command works on the project in the current folder, or on the project folder given as an optional last argument.

Finding packages

Three read-only commands show what is available. They never change your project or the download cache.

sarlin package-search lists every package in the Nook with its newest version. Give it one word to keep only the packages whose name or description contains it, ignoring case:

sarlin package-info csv shows one package in detail: its description, licence, repository and every published version, newest first. When you run it inside a project that already requires the package, it adds a line saying which version the project uses and whether a newer one exists.

sarlin package-list lists the packages the current project requires, with a note on those that have a newer version. A package added straight from GitHub is shown with its address instead of a description.

Descriptions come from the Nook, so they are written by package authors. Control characters are removed before they are printed. If the Nook cannot be reached, the commands use the copy saved the last time it was available and say so.

Adding a package

Adding a package

sarlin add csv looks the package up in the Nook and adds its newest version. sarlin add csv@0.1.1 adds a specific version.

The command writes one line to sarlin.project. Every other line, blank line and comment in the file is left exactly as it was.

A require: line is the package name and an exact version. There are no version ranges: the version you write is the version you get. Adding a package that is already required changes its version, and adding the same version again changes nothing.

The package's files are now part of the project, so its classes and functions can be used directly:

check, build and run fetch any package that is not downloaded yet, so a freshly cloned project builds without any extra step.

Adding from GitHub directly

sarlin add github.com/owner/repo adds a package that is not listed in the Nook. The newest version tag in that repository is used, and the package name is the name from its own sarlin.project, in lower case with spaces and hyphens turned into underscores. Because there is no Nook entry to say where the package lives, the address is recorded on the line:

Only GitHub addresses of the form https://github.com/owner/name are accepted.

The lock file

Alongside sarlin.project, the compiler keeps sarlin.lock. It records the exact commit of every package in the project, including packages required by other packages:

Builds use the commit in the lock file, so a package cannot change underneath you, even if its author moves a tag. Commit both files to version control. The lock file is rewritten only when its content changes, and it is deleted when the last package is removed.

Removing and updating

sarlin remove csv deletes the require: line and the lock entry. sarlin update moves every required package to its newest version and never moves one backwards. It prints one line for each package that changed, such as updated csv from 0.1.1 to 0.1.2, or all required packages are up to date.

To see whether newer versions exist without changing anything, run sarlin update --check. It prints one line per package that can be updated, and exits successfully either way, so it is safe in scripts:

It prints all required packages are up to date when nothing is newer. It never changes sarlin.project or sarlin.lock and never downloads a package.

Name collisions

Name collisions

Sarlin has no namespaces yet. A class, define, callable, signal, function or global declared in a package shares one set of names with your own code and with every other package, so two definitions of the same name cannot be built together.

sarlin collisions reads every file in the project and its packages and reports each name that is defined more than once, with where each definition lives. It runs automatically after sarlin add and sarlin update, so a clash is reported when you add the package rather than at build time.

When nothing clashes it prints:

As a command on its own it exits with status 1 when it finds a collision, so it can be used in a script or in continuous integration. After add and update the same warnings are printed but the command still succeeds, because adding the package worked.

A collision still stops the build

The report is a warning, not a fix. Until namespaces exist, the build fails with the usual duplicate error until you rename your own definition or remove one of the packages.

Writing a package

A package is a Sarlin project in a public GitHub repository, with its files under source/ and its own sarlin.project:

  • A package must not define func main. The program entry point belongs to the project that uses the package, and the compiler reports a package that defines one.
  • Packages may not contain symbolic links. The .sar files under source/ are compiled, plus any C files the package names with native:.
  • A package that wraps a C library sets include:, link:, native: and macro: in its own sarlin.project, and they carry over to every program that requires it. See Foreign functions.
  • A package can require other packages with its own require: lines. They are resolved into one flat set with a single version of each package; two different versions of the same package, or a cycle, is an error.
  • Choose distinctive names for what the package defines, since they share one set of names with every project that uses it.
  • A version is a git tag such as v0.1.0 in the repository, made of three numbers and no suffix.

To list the package in the Nook, add one small file to the Nook repository in a pull request; the Nook page has the steps.

Where packages are stored

Downloaded packages are kept in a cache shared by every project, in .sarlin/nook in your home folder (%USERPROFILE%\.sarlin\nook on Windows). Set the SARLIN_NOOK_HOME environment variable to use another folder.

A project whose packages are all in the lock file and in the cache needs no network access. If the Nook cannot be reached but a cached copy of its list exists, the compiler says so and uses the cached copy.
